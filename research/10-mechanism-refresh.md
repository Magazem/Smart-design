## §6 — Changelog: other mechanism changes between v2.5.0 and 2.13.0 that affect what we'd clone

- **`_find_reasoning_rule` lost its fallback tiers.** v2.5.0 tried exact match, then substring match, then keyword-token match (report 01 §1.3, `design_system.py:64-86` in that version). Current version (`design_system.py:357-363`) is **exact match only** (casefold + strip, one comparison, `return {}` otherwise). This makes the `UI_Category` ↔ `Product Type` text-identity requirement (Tier 1.4 in the corrections) even more load-bearing than reports 07/08 assumed — there is no longer a partial-match safety net if the strings drift even slightly.
- **`parse_decision_rules` is not wrapped in try/except at its call site in `design_system.py`.** `_apply_reasoning()` (line 385) calls it directly; if a row's `Decision_Rules` JSON ever contains an unrecognized condition key, this raises `ValueError` uncaught at that point in `design_system.py`. `validate_data.py` catches this offline before publishing (`validate_data.py:361-365`, wrapped there) — so a validated CSV is safe, but this is a preflight-only guarantee, not a runtime one. If validation is ever skipped, a bad key doesn't silently do nothing (as reports 07/08 correctly described for the OLD version) — in the current version it can crash the live `--design-system` search for any query that resolves to that category. Worth flagging as a reason to always run `validate_data.py` before shipping any new CSV row.
- **`ui-reasoning.csv` gained two columns**: `Reasoning`, `Confidence` (now 12 columns total, up from 9). `Confidence` must parse as a float in `[0, 1]` if present (`validate_data.py:378-384`) — matches the rebuild report's "Confidence must be 0-1 (now 0.9)" note.
- **`Decision_Rules`' JSON grammar changed shape.** v2.5.0 example: `{"if_ux_focused": "prioritize-minimalism"}` — condition → single string. Current: `{"if_ux_focused": ["style:minimalism-and-swiss-style"]}` — condition → **array** of `prefix:value` action tokens (verified directly against a live row, `ui-reasoning.csv:2`). Any pre-existing v1-style single-string values would fail `parse_decision_rules`'s `isinstance(actions, list)` check (`reasoning_contract.py:78`).
- **`colors.csv`, `typography.csv`, `products.csv` column sets are unchanged** (19, 11, and 9 columns respectively — read and counted directly, identical to what report 01 documented). The Tier-1 column-name fixes reports 07/08 asked for on these three files are still correct advice under current upstream.
- **`styles.csv` search now includes an "active-only" filter and an exact-identity short-circuit.** `search()` (`core.py:755-845`) first tries `_style_identity()` — an exact or high-confidence substring match against `Style ID`/`Style Category`/`Aliases` — before ever running BM25, and BM25 style search is restricted to rows where `Status == "active"` (`core.py:810-814`). A style row with `Status` left blank or set to anything other than `active` (the draft never set a `Status` value at all in some earlier iterations) would be **silently excluded from ranked search** even though it can still be reached via exact-identity match. Worth double-checking the ENS style row's `Status` is explicitly `"active"` (the rebuild report does list `Status: active`, `ENS-plugin-rebuild-v2.md` line 76 — correct).
- **`data-provenance.json` and `catalog-summary.json` are new, validated files** with no v2.5.0 equivalent — confirmed to exist and be checked (`validate_data.py:900-998`).
- **BM25 engine itself changed materially**: added synonym normalization (`_SYNONYMS`, e.g. "colour"→"color", "e-commerce"→"ecommerce"), score-floor/coverage/margin "abstain" thresholds per domain (`_DOMAIN_SCORE_FLOORS`, `_SEARCH_THRESHOLDS`) so a low-confidence match now returns **zero results with suggestions** instead of a weak top-1 guess, and a domain-specific query-rewrite table (`_DOMAIN_QUERY_REWRITES`). This is a real, positive change for ENS: a query like `"ENS formulaire"` that clears the `product`/`style`/`color` score floors will return ENS confidently; one that doesn't clear the floor now returns **no result plus suggestions** rather than silently handing back a generic row — arguably a better hard-fail primitive than the rebuild report's custom `ens-search.sh` wrapper, built into upstream itself. Not confirmed whether the ENS row's queries reliably clear these per-domain floors — would need to run the actual thresholds against the final CSV rows.
- **Stack coverage grew from 15/16 to 22** (added `javafx`, `wpf`, `winui`, `avalonia`, `uno`, `uwp`), each stack row now also carries freshness/status metadata (`STACK_CURRENT_VERSIONS`, `STACK_STATUSES` including `"unverified"`) validated by `_check_stack_freshness_contract`. Not relevant to ENS directly, noted for completeness.
- **Windows symlink issue from report 04 is fixed upstream.** Current `CLAUDE.md` states explicitly: *"There are no symlinks in this repo (git-on-Windows checks them out as plain text files pointing at a path, which silently breaks the skill) — every mirrored copy below is a real, independently-committed file kept in sync by `cli/scripts/sync-assets.mjs`, enforced by the 'Check asset sync' CI workflow."* Report 04's finding that the repo's own skill was broken as checked out on Windows no longer applies to current upstream.
- **The four-independent-descriptions drift (report 04) is partially fixed.** `plugin.json`, `skill.json`, and `marketplace.json` `version` fields all agree at `2.13.0` now (previously observed out of sync). The `description` *text* across these files still differs in wording and in the literal stack list (`marketplace.json`'s plugin description names 16 stacks by hand while the metadata line claims 22), so full description-copy convergence is still not achieved, but the version-number drift specifically is resolved.
- **`design.csv`, the orphaned file report 01 §1.8 flagged, no longer exists** in current upstream's `data/` directory at all (checked directly — 13 CSVs present, `design.csv` is not one of them). Whatever it was is gone, not merely unwired.
- **`persist_design_system` no longer silently overwrites an existing `MASTER.md`.** New default behavior: if `MASTER.md` already exists and `force` is not passed, the result status is `"skipped_exists"` (`design_system.py:995-1061`); overwriting requires an explicit `force=True` / `--force`. Writes are also now atomic (temp-file + rename, `_write_persisted_file`, lines 972-991) rather than a direct open-and-write. I did **not** find any script that reads `MASTER.md` back in (grepped for `MASTER.md` across `scripts/` — only writers and tests reference it, no reader) — the "inherit" half of the loop still appears to be pure convention (SKILL.md instructs the model to open the file itself), consistent with reports 01/05's finding, just now with a safer, idempotent writer. This check was not as exhaustive as items 1-5 above; treat it as a reasonable-confidence read, not a certainty.
