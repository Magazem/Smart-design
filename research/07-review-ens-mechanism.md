## Section 2 — Trigger block

| Draft quote | What report 04 established | Will it work? | Fix |
|---|---|---|---|
| "Trigger block... replaces the current 'Company Defaults' paragraph **in all 7 skills**" — shown as a `>` blockquote under a `##` heading | `research\04-packaging.md` §1.2 "Loading model" (confirmed against Anthropic's own docs): activation is a **two-tier** decision. Tier 1 (always loaded, ~100 tokens/skill) is **only** the YAML frontmatter `name` + `description`. Tier 2 (the SKILL.md **body** — where a blockquote like this one lives) is loaded **only after** Claude has already decided, from the description alone, that the task matches. | **NO — as drafted, this does not fix the skipping bug.** The trigger block is body content. Nothing in Section 2 edits the frontmatter `description:` field. If the description Claude checks *before* opening the file doesn't mention ENS-relevant triggers (document types, "note interne", "formulaire", "ENS", "Bettembourg", brand/company name), the skill is never loaded at all on a given task — the mandatory workflow block, the "never invent colors" prohibition, everything in Section 2, is simply never read. This is consistent with the reported symptom: skipped on 2 of 3 documents, and an invented ENS color on the 3rd even when told "use the ENS brand" — the model had no brand data loaded because the skill never activated, so it guessed. | The `description` field (not just the body) needs to be rewritten to name the concrete triggers: the org name ("Eng nei Schaff", "ENS", "a.s.b.l."), the document types (note interne, formulaire, fiche, affiche, dépliant, présentation), and ideally the always-produce-branded-output framing ("this organization's documents must never use generic/default branding"). Without a description change, nothing else in the draft can take effect, because the model never gets far enough to read it.
| Step 3: "Run the search prefixed with ENS... **if the result is not ENS, the query is wrong — fix the query, do not use a generic palette.**" | No code anywhere checks the search output against an expected brand/product-type string. This is the same category of enforcement as the MASTER.md "read this file next time" convention documented in `research\01-mechanism.md` §1.4a — pure instruction text, no assertion, no exit code, nothing resembling `html-token-validator.py`'s hard-fail-on-noncompliance pattern. | **NO mechanical enforcement — it is an instruction the model may ignore**, exactly as the assignment suspected. Nothing forces the model to (a) actually inspect whether the returned row's `Product Type`/`Style Category` says "ENS", (b) notice a mismatch, or (c) retry with a different query rather than proceeding with whatever a generic-row hit returned. | If this check needs to be real rather than advisory, it has to be a script, not a sentence — e.g., a thin wrapper around `search.py` that greps its own stdout for "ENS" and exits non-zero (or prints an explicit `[NO ENS MATCH]` marker) if absent, the same hard-fail pattern `html-token-validator.py` already uses elsewhere in this codebase. As written, this is prose enforcement layered on top of a BM25 engine that has no concept of "the right answer" — it can only return "the highest-scoring row for this exact query," which is not the same guarantee.

## Bottom line

Section 1's CSV additions will *partially* work as literal BM25 bait (the `products.csv` row should reliably surface on any query containing the token "ens"), but three of the five proposed rows have column-name mismatches or missing required search fields (`colors.csv` is missing its own search key entirely), and the centerpiece of the draft's per-document routing — `Decision_Rules` JSON — is inert; it is never evaluated by any code path, confirmed against `research\01-mechanism.md`. Section 2's trigger block, however well-written, is written into the wrong tier: it edits body content that only loads after activation already succeeded or failed, and the draft never touches the `description` field that actually gates activation — so the exact skipping behavior the user is trying to fix has no reason to change.
