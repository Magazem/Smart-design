## Required re-check: does Decision_Rules actually execute a fixed built-in set?

v2's claim: *"Decision_Rules is read (`design_system.py:385`) but only a fixed set of built-in condition keys (`if_ux_focused`, `if_data_heavy`, `must_have`…) can ever fire."*

Checked directly:
- `design_system.py:385` is inside `format_ascii_box()`'s **Typography** section — it's `lines.append(line.ljust(BOX_WIDTH) + "│")`, part of the ASCII-box text wrapper for the "Best For" line. It has nothing to do with `Decision_Rules`. This is a wrong citation.
- The only place `Decision_Rules` is actually touched in code is `design_system.py:107-109` (`json.loads(rule.get("Decision_Rules", "{}"))`, wrapped in try/except, discarding on parse failure) and `design_system.py:244` (`"decision_rules": reasoning.get("decision_rules", {})`) — it is parsed and passed straight into the output dict. **Nothing reads that dict key back out and branches on `if_ux_focused` / `if_data_heavy` / `must_have` or any other key, anywhere.**
- Repo-wide grep for `if_ux_focused|if_data_heavy|must_have|decision_rules|Decision_Rules` across the entire plugin: every hit is either (a) the CSV column header/data itself, or (b) `_sync_all.py`'s `derive_ui_reasoning()` (lines ~314-327), which only **writes** those key names into a JSON string for new rows it generates — it never reads them back either. No evaluator exists anywhere in the codebase.

**Verdict: the original finding is correct, v2's revision is wrong.** Nothing evaluates `Decision_Rules` — not "only a fixed built-in subset," but *literally none of it, ever*. There is no list of built-in keys to know, because there is no evaluator. This doesn't change the recommended fix (keep it as documentation, drive real routing from the trigger block), but the false claim should be corrected before it gets copied into a README or handoff doc as if it were a documented feature.
