## 4. Release cadence

- 25 GitHub Releases between v2.5.0 (2026-03-10) and v2.15.0 (2026-08-13) — **156 days, ~1 release every 6.2 days on average**, though real cadence is bursty: several same-day patch clusters (v2.6.1–v2.6.5 across 3 days; v2.11.1–v2.11.5 across 5 days; v2.14.0–v2.14.2 in one day) driven by `semantic-release` auto-cutting a new tag on every qualifying merge to `main`, not by a fixed schedule.
- Cadence increased sharply after **v2.6.0 (2026-06-22)**, when `feat(release): add semantic release automation` (PR #375) went in — before that, v2.0.0→v2.5.0 (2026-01-16→2026-03-10, 53 days) covered only 6 releases, a much slower, manually-tagged cadence.
- As of 2026-09-07, `main` has accumulated 24 unreleased commits over 24 days since v2.15.0 with no new tag cut yet — consistent with the established rhythm (a release every ~week), so a v2.15.1/v2.16.0 is plausible within days, not months.
- **Practical implication for staleness**: anything we clone or reference in upstream today has a realistic shelf-life of **single-digit days to about two weeks** before upstream's own code moves again. A "v2.5.0 vs v2.13.0 vs v2.15.0" three-way mismatch inside our own research already happened within 5 months — re-verify against current `main` immediately before implementation, not against any cached research snapshot, including this one.

## 5. Does the local marketplace checkout auto-update, or is it pinned? Why is it 5 months old?

**Pinned — confirmed from two independent angles, both pointing the same way:**

- **Claude Code's own plugin-install mechanic pins to a commit SHA at install time and does not silently advance it.** (Sourced from Anthropic/community documentation on plugin marketplaces, cross-checked 2026-09-07: "When you install a plugin, Claude Code records the commit hash at that moment and never checks again," and "a marketplace refresh is not the same as updating the plugin you already installed — refreshing the marketplace alone does not change the plugin version you are already using." `/plugin marketplace update` refreshes the catalog metadata only; pulling new plugin code requires a separate, explicit plugin-update action.) The local checkout's `.claude-plugin` config (`plugin.json:1-11`, report 04 §1.1) has `"skills": ["./.claude/skills/ui-ux-pro-max"]` sourced from `"./"` (the repo root at whatever commit was pinned) — there is no version constraint or auto-tracking field in that manifest; it is a static pointer.
- **Directly observed on this machine**: `git log -1` on `C:\Users\ysuliman\.claude\plugins\marketplaces\ui-ux-pro-max-skill` shows HEAD at commit `b7e3af8`, dated **2026-04-03**, tracking `origin/main` as a remote but never re-fetched/re-merged since — it is genuinely frozen at a commit made ~3 weeks after the v2.5.0 tag. That fully explains "why is the local copy 5 months old": nothing in Claude Code's plugin system polls for or applies upstream changes automatically; the checkout only moves when a human re-installs or explicitly updates it, and neither happened here.

**Separately — and this is the more important finding, because it explains the synthesis's version-skew confusion rather than just restating it:** upstream's *own* version-manifest fields (`skill.json`, `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`) are themselves stuck reporting **"2.13.0" as of current `main` HEAD (2026-09-06), five releases and one major mechanism overhaul (v2.15.0) after that number stopped being true.**

Evidence chain:
1. `.releaserc.json` on `main` scopes `@semantic-release/npm` to `"pkgRoot": "cli"` — semantic-release only ever bumps/publishes the CLI's npm package version; it has no built-in step for the repo-root `skill.json`/`plugin.json`/`marketplace.json`.
2. Upstream noticed this gap and built `.github/workflows/bump-versions.yml` (merged via PR #439, "feat(ci): auto-bump skill JSON versions after release," 2026-08-06T00:29:06Z) — triggered on every `release: published` event, it `jq`-patches all three manifest files to the new version and **opens a pull request** (it does not commit directly to `main`).
3. The one and only manifest-bump PR that was actually merged is **PR #438, "fix: bump skill.json version to 2.13.0," merged 2026-08-06T01:29:02Z** — i.e., the last real sync point is v2.13.0.
4. Every release since (v2.14.0, v2.14.1, v2.14.2, v2.15.0) should have triggered workflow #439 and produced a follow-up "bump skill.json version to 2.14.0" / "...2.15.0" PR. **No such PR exists** in the repo's PR history (checked via `gh pr list --search "bump"`, all results enumerated in §2's research — none past #438/#439). Direct content check confirms the effect: `skill.json`, `plugin.json`, and `marketplace.json` on current `main` still read `"version": "2.13.0"` verbatim, even though the actual code at that same `main` HEAD is v2.15.0-plus. (`cli/package.json` in git is even more stale, at `"2.5.0"` — semantic-release's npm publish step evidently doesn't commit its own version bump back into the repository file either; only the ephemeral CI-time value gets published to npm, which is why the npm registry correctly shows 2.15.0 while the checked-in `cli/package.json` does not.)

**Conclusion, stated plainly:** the number "2.13.0" that the synthesis and the rebuild report used to describe "the user's installed plugin" is very likely an accurate *read of the manifest field* but a **false signal of actual code content** — upstream's own automation to keep that field honest silently stopped working after one run. Anyone (including a Claude instance running the live plugin) that reports its own version by reading `plugin.json`/`skill.json` will say "2.13.0" regardless of whether the underlying installed commit is actually v2.13.0, v2.15.0, or `main` HEAD. This is upstream's bug, not a Claude Code platform limitation, and it independently explains why v2.15.0-only artifacts (`reasoning_contract.py`, `data-provenance.json`, the 29-column `styles.csv`) could plausibly have been observed by a live instance "reporting" v2.13.0 — the report field cannot be trusted to gate what code is actually present; only a direct file check (as done throughout this document, and as report 01/07/08 should now redo against current `main`) can.
