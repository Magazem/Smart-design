# Review — ENS draft §3 (per-document rules) vs. research\03-document-design-knowledge.md

Scope: Section 3 only (Global + Types A–E). Checked against the thresholds I established in
report 03. Where report 03 doesn't cover something, I say so rather than inventing a
threshold. Legend: **OK** consistent · **WRONG** contradicts a [FACT] · **RISKY** contradicts
a [CONVENTION] or sits below/near a threshold · **MISSING** report 03 requires a rule this
type doesn't have.

| # | Location | Draft wording (quoted) | Verdict | Basis / correction |
|---|---|---|---|---|
| 1 | Global — type scale | "Type scale (pt): 7.5 label · 8 caption · 10 body · 12 lead · 16 H3 · 24 H1" | **RISKY** | Report 03 sets no print body-size floor (only a projection floor for decks). Applying general print/accessibility convention instead: 7.5–8pt is the low end of what's normally used for captions/fine print, not labels meant to be read at a glance by a general public audience (report 03 §A notes many ENS readers are non-native French speakers — smaller type raises the reading-effort bar exactly where the org's own key-considerations row says it shouldn't). Not a report-03 threshold violation, but flagged as a genuine risk, not just aesthetics. |
| 2 | Global — footer | "Footer on every printed page: … + Page x / y" | **N/A** | Report 03's header/footer concern (§A) is specifically that ATS parsers skip header/footer regions on CVs. These are internal memos/forms read by humans, not machine-parsed résumés — doesn't apply. No print concern either; a contact footer is standard practice for internal print docs. |
| 3 | A. note-interne — margins | "A4, margins 25 mm sides / 20 mm top-bottom" | **OK** | Report 03's margin numbers (3–6mm) are bleed/trim safety margins for professionally trimmed print (§C) — not applicable to a standard office-printed A4 letter, which has no trim step. 25/20mm is a generous, conventional business-letter margin; no conflict. |
| 4 | A. note-interne — measure/CPL | Body = 10pt (Global scale), column width = full text block at 25mm margins on A4 | **MISSING** | Report 03 §D sets 45–75 characters-per-line as the readable range (Bringhurst). A4 width 210mm − 50mm margins = **160mm measure** = 453.5pt. At 10pt Arial (~0.5em avg character width ≈ 5pt/char) that's **~85–95 characters per line** — well outside the 45–75 range, on the "losing the line on the return sweep" end. The draft never states a measure/column-width rule for note-interne body text; at the given margins and body size, one is needed. Fix: either narrow the effective measure (e.g., a secondary margin/rule column, since bleed-style margins don't apply here — a text-only inset would work) to ≤~130mm, or raise body size toward 12pt to bring CPL back under 75. |
| 5 | A. note-interne — tables | "uppercase tracked column labels, 1pt dark rule under header, 0.5pt hairlines between rows, no fills, no zebra" | **OK** | Matches report 03 §D table-design convention directly (minimize vertical rules, sparse horizontal rules, no per-row fills) — this is literally the Tufte data-ink-minimization rule I cited. Good match. |
| 6 | A / typography.csv — DOCX font | "Fallback (Word, no embedded fonts): Arial / Arial" / "Font Arial (Word)" | **OK** | Matches report 03 §B safe-font-stack finding directly: Arial ships on effectively all Windows installs, so it sidesteps the embedding-is-opt-in-and-license-gated / silent-substitution failure mode entirely. Correct call for an editable .docx that must open identically on any office PC. (Whether the generation tooling — python-docx — is actually available is a separate, non-design question; doesn't affect this verdict.) |
| 7 | A. note-interne — PDF copy | "output: .docx (+ PDF copy)" | **OK** (minor note) | Not flagged in the draft, but worth stating: a PDF exported from Word normally embeds fonts automatically as part of PDF generation, so the Arial-vs-Manrope question is moot for the PDF copy specifically — the embedding risk in report 03 §B is a DOCX/PPTX-native-format problem, not a PDF-output problem. |
| 8 | B. formulaire — margins | "A4, margins 16 mm sides / 12 mm top-bottom" | **OK / not applicable domain** | Same caveat as #3 — report 03's margin thresholds target trimmed print, not office A4. 12–16mm is comfortably clear of the ~4–8mm non-printable edge zone typical of office printers/photocopiers (a separate concern from report 03, general print knowledge, not one of my established thresholds) — no conflict either way. |
| 9 | B. formulaire — green rule | "one green rule under the title" / "1pt dark rule … green rule" as structural line | **OK** | Computed L* of #1F6F43 vs white ≈ 41.3, delta ≈ 58.7 — clears report 03 §E's ~40–50 L* floor comfortably. Fine as a rule/line element, which doesn't need to be character-legible. |
| 10 | B. formulaire — section number | "number in green (7.5pt bold)" + "everything black/dark except the green rule and section numbers — a form must photocopy cleanly" | **RISKY** | The color itself clears the L* floor in full-color print (#1 above), but the draft's own stated requirement is monochrome photocopy fidelity. On a black-and-white copy, #1F6F43 (L*≈41) renders as a mid-dark *gray*, not black — at 7.5pt that's a real legibility drop versus true black (L*0) text, and small/thin glyphs are exactly what degrade first across copy generations. The rule wants photocopy-safe **and** uses a mid-lightness color at small size for the one thing meant to stay legible after that copy — those two goals are in tension. Recommend true black for the section number, with green reserved for the rule lines only (which don't need to survive photocopying as legibly). |
| 11 | B. formulaire — legal text | "Legal/regulatory text is printed verbatim, 7.4pt uppercase, under its own green rule" | **RISKY — most severe finding in this review** | Stacks three legibility risks on the one piece of text that legally must not be misread: smallest point size in the whole scale (7.4pt), sustained uppercase (established typographic convention: extended all-caps text loses word-shape cues and reads slower than mixed case — this compounds, it doesn't just coexist with, the small size), and photocopy degradation (#10). Report 03 doesn't set a numeric floor for this, but the compounding of all three factors on regulatory text is the single highest-risk item in the draft. Recommend: mixed case (or at minimum increase size, e.g. 8–8.5pt) for verbatim legal text specifically. |
| 12 | B. formulaire — numeric code columns | "numeric code columns use tabular figures, left-aligned" | **OK, with a distinction worth stating** | Report 03 §D says right-align numeric columns / left-align text columns, for columns where *magnitude* is compared (financial figures, quantities). "Code" columns (reference numbers, postal-style codes) are conventionally treated as identifiers, not quantities — left-alignment is standard practice for ID-like numeric strings since there's nothing to compare by size. Tabular figures are still correct and matter more here (so digits/characters line up column-to-column for scanning). Not a contradiction — just confirm this is genuinely an identifier column and not a quantity column before applying it elsewhere. |
| 13 | D. slides — body size | "body Inter 18–20pt" | **RISKY** | Report 03 §B: 24pt is the floor for general projected bullet/body text; 18pt is reserved specifically for dense data callouts, "never smaller" than that as an absolute floor. The draft sets 18–20pt as the *default* body size for all slide content, not a callout-only exception — that's using the absolute floor as the baseline. Recommend 24pt+ as default, with 18–20pt allowed only for dense/data-heavy slides as the exception the report describes. |
| 14 | D. slides — output format / fonts | "output: PPTX for the manager" + typography.csv: "Use Manrope/Inter whenever fonts are embedded (PDF, HTML, images). Use Arial in editable Word/Excel files" | **MISSING** | PPTX isn't in either bucket — not "PDF/HTML/images" (embedded-by-default) and not "Word/Excel" (Arial fallback). PPTX is exactly the format report 03 §B flags as the highest-risk one: font embedding is opt-in (File→Options→Save) *and* gated by the font's own embedding-permission bit, and un-embedded + not-installed = silent substitution (the actual "deck looks broken on the client's machine" failure mode). Good news: Manrope and Inter are both Google Fonts under the OFL, which permits embedding — so licensing isn't the blocker. But the rule needs to explicitly say: embed fonts must be turned on for every PPTX export, and it should be verified (not assumed) rather than left implicit by omission. As written, a generated PPTX using Manrope/Inter without that explicit step is a font-substitution incident waiting to happen. |
| 15 | D. slides — bullet count | "max 5 bullets" | **OK** | Stricter than report 03's 6×6 heuristic (max 6/6) — no conflict, tighter is fine. |
| 16 | C. social | Grid/kicker/tile specs, pixel-based | **Out of scope for report 03** | Report 03 doesn't cover social-media graphic specs (pixel grids, safe zones, tile layout) — no basis to verify these, flagging as uncovered rather than guessing. |
| 17 | C. social — lime as text | "Body: Inter 23–27 px, key words in lime #C9F27A" (on green background per section intro) | **OK, borderline** | Computed L* of #C9F27A ≈ 90.5 vs green #1F6F43 ≈ 41.3 → delta ≈ 49.2, right at the top edge of report 03's 40–50 L* floor. Passes, but with little margin — this is a screen graphic though (print-contrast proxy is a stand-in check here, not a native fit), so treat as a soft pass, not a confident one. |
| 18 | E. web-tool | Radius/buttons/icons/sticky-header specs | **Out of scope for report 03** | Screen/UI design system territory, not covered by this research pass (CV/deck/print/report domains). No verdict — defer to whoever covered UI/UX-side conventions. |
| 19 | 5 types overall — professional print production | No type in the draft is sent to a commercial print shop (note-interne = office/Word, formulaire = office PDF/photocopy, social = PNG, slides = PPTX/HTML, web-tool = HTML) | **N/A, correctly absent** | Report 03 §C (bleed, CMYK conversion, DPI floors, spot vs process, paper stock) doesn't need to appear anywhere in this draft — none of the five types are professionally printed. Correctly not covered. This changes the moment a professionally-printed type is added (see [À valider] #6 below). |
