# research/66 — two-stage column census (CSV → resolved → emitted), reconciled with research/64

Reproducible via `python3 research/census_columns.py`. Full run captured verbatim in
`research/census_columns_output.txt`.

**Why a second census.** research/65 measured only stage 2 (resolved → emitted by the four
`_build_*_lines` handoff builders) and called "resolved" whatever `resolve.py` already
emitted for its one representative doctype (`cv-us`). That missed the earlier defect: for
eight tables, `data/schema-manifest.json`'s `display_columns` are either undeclared
(`cv-regions`, `doctypes`, `doc-reasoning`, `doc-styles`) or incomplete (`typefaces`,
`palettes`, `page-formats`, `render-targets`), so `resolve.py` never puts most of a row's
columns in the resolved JSON at all — they are invisible to a stage-2-only diff. This
census adds stage 1: raw CSV columns (`schema-manifest.json` `columns`, generated by
`research/build-manifest.py`) vs. what `resolve.py`'s own `_display_columns(spec)` exposes.
Stage 1 is pure manifest metadata — it needs no doctype walk and is identical for every row
of a table.

**Counting rule (research/64 D-B):** denominator = full raw CSV column count, which
*includes* the table's own key column; numerator = `len(display_columns) + 1`, the `+1`
crediting the always-present key → `"key"` rename (a rename, not a drop). This is the exact
convention research/64 used for its `"X of N"` figures, confirmed by exact reproduction
below.

## 2. Gap classification — stage 1

**DEFECT — six tables missing declared payload columns, upstream of any handoff
concern**: `cv-regions`, `doc-reasoning`, `doc-styles`, `typefaces`, `palettes`,
`page-formats`, `render-targets`, `doctypes` (eight, matching research/64's list exactly).
Root cause per research/build-manifest.py:33-45's own comment: `display_columns` is a
hand-authored *superset* declaration — "today's default... PLUS every column `ddi.py
handoff` reads out of that table" — and it was written for only the tables research/54
part 3 identified (`structures`, `headings`) plus the four research/64 confirmed FIXED
(`constraints`, `type-scales`, plus those two). The other eight tables either have no
`display_columns` key at all (fall back to `resolve.py`'s bare-minimum default:
`searchable_columns` + the table's own FK source columns) or a declared list that was
never extended to cover values a renderer needs (`typefaces`, `palettes`, `page-formats`,
`render-targets`). This is a single root cause — an incomplete/missing declaration in one
generator file — repeated across eight tables, not eight separate defects.

**Gap columns split into two kinds within each table**, cited so a fix can tell them
apart:
- *Identity/search metadata that plausibly belongs in the gap regardless* — none observed
  at stage 1; `Display Name`/`Keywords`/`Best For` are already IN the declared
  `display_columns` or default `searchable_columns` for every table that has them
  (confirmed by their absence from the stage-1 gap lists above). The INTENDED
  identity-metadata classification research/65 made applies at **stage 2** (columns that
  *do* resolve but a renderer correctly never reads), not here.
- *Design/render-relevant values genuinely absent from the resolved JSON* — e.g.
  `cv-regions`'s `Seniority Band` (the only column distinguishing `uk-early` from
  `uk-experienced`), `doc-reasoning`'s `Anti-Pattern Tokens`/`Severity` (the "looks like
  AI" material the skill's own description advertises), `doc-styles`'s `Table Rules`/
  `Table Fills`/`Emphasis Mechanism` (its entire visual specification), `typefaces`'s
  `Has Tabular Figures`, `palettes`'s `On Primary`/`On Secondary`/`Text-Safe Roles` (no
  column says what foreground colour is legible on a fill), `page-formats`'s `Fold Type`/
  `Panels mm`/`Measure mm` (a tri-fold's physical structure, research/64 D-C). All DEFECT.

**INTENDED (not a gap, but worth naming explicitly) — `Brand Scope` absent from
`doctypes`/`doc-styles`/`palettes`/`typefaces` display_columns**: not investigated for a
citation in the time box; carried forward as unclassified rather than asserted either way.

**figures/font-substitutes (out of scope, unreachable at resolve.py level)**: no
`foreign_keys` entry anywhere in the manifest names either table, so no doctype's FK walk
ever reaches them — 0 rows resolved regardless of `display_columns`. This is a resolve.py
reachability gap, not a `display_columns` gap; fixing `display_columns` for these two
tables would do nothing until something points a foreign key at them. Same class as
research/64 D-H. Out of this census's and W3's scope (Manager D5).

## 6. Root-cause verdict

**Stage 1 — one cause, eight instances.** `research/build-manifest.py`'s `display_columns`
declaration is a hand-authored superset list (per its own comment, lines 33-45) that was
extended for the tables research/54 part 3 and the v0.3 fix touched, and never extended
for the other eight. Not a schema/data problem — the CSV values exist; the generator's
declaration for these eight tables was simply never written or never finished.

**Stage 2 — two causes, matching research/65 exactly** (unaffected by the stage-1 finding,
since these are downstream of columns that DO resolve):
1. **Builder asymmetry** (Font Rule): pdf/png builders have a render-target-conditional
   embed/fallback branch; docx/pptx builders print both unconditionally — written earlier,
   never revisited.
2. **Missing `HANDOFF_VOCAB` entry** (doc-styles): no builder reads the table at all,
   compounding the stage-1 defect (its design columns don't resolve either).

## 7. Applicability source of truth

**No, it does not exist today**, at either stage, independent of the generator/vocab that
also defines it:
- Stage 1: whether a column resolves is governed entirely by
  `research/build-manifest.py`'s `display_columns` declaration — a hand-maintained
  superset list with no independent check that it actually contains every column a
  downstream consumer needs. A test that reads this declaration to assert a column
  resolves is checking the generator against itself.
- Stage 2: `HANDOFF_VOCAB` (ddi.py:208-262) is simultaneously the schema-column-to-vocab
  name map AND the only record of which columns are "applicable" to the handoff — absence
  from it is silently treated as not-applicable, with nothing else to check it against.

Two places a real declaration could live (not implemented, per scope):
- **`schema-manifest.json` column metadata** (e.g. a per-column `"handoff": {"docx": true,
  ...}` block or reason string). Pro: single source of truth co-located with the schema;
  a `validate_data.py`-style structural check could enforce it. Con: couples the schema
  file (today DATA-shape-only) to a downstream presentation concern; a new render path
  needs a manifest change, not just a `ddi.py` change.
- **A single explicit applicability table in `ddi.py`**, separate from `HANDOFF_VOCAB`'s
  naming duty (e.g. `HANDOFF_APPLICABILITY = {("doc-styles", "Table Rules"): {...}, ...}`).
  Pro: stays in the file owning rendering concerns; a test can diff it against what each
  builder actually reads (the same `.get()`-tracking technique this census uses), without
  touching the manifest. Con: a second hand-maintained table that can itself drift from
  the builders, same maintenance risk `HANDOFF_VOCAB` already carries for names.

Note: stage 1 needs its own, separate applicability declaration — a `HANDOFF_APPLICABILITY`
table in `ddi.py` alone cannot fix a column that never reaches the resolved JSON in the
first place; that requires a `display_columns`-side fix regardless of which stage-2 option
is chosen. Not implemented here, per task scope (no `ddi.py` or `build-manifest.py` edits).
