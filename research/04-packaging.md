# Packaging and Distribution

## 1. Findings

### 1.1 Package format — upstream dissection
Repo root: `C:\Users\ysuliman\.claude\plugins\marketplaces\ui-ux-pro-max-skill`

- `skill.json` (repo root, `skill.json:1-41`) — **not** a Claude concept at all. It's the package's own generic-installer manifest: `name`, `displayName`, `description`, `version`, `author`, `license`, `homepage`, `repository`, `keywords`, `platforms` (18-entry array: claude, cursor, windsurf, copilot, kiro, roocode, kilocode, codex, qoder, gemini, trae, opencode, continue, codebuddy, droid, warp, augment, antigravity), and `install: "npx uipro-cli init --ai {{platform}}"`. This file drives their own multi-tool CLI, not Claude's plugin system.
- `.claude-plugin/plugin.json` (`plugin.json:1-11`) — the **Claude Code plugin manifest**. Fields: `name`, `description` (a *second*, differently-worded description — this is the one shown in `/plugin` listings, distinct from the SKILL.md frontmatter description used for activation), `version`, `author.name`, `license`, `keywords`, and `skills: ["./.claude/skills/ui-ux-pro-max"]` — an array of relative paths telling Claude Code which skill directories this plugin exposes.
- `.claude-plugin/marketplace.json` (`marketplace.json:1-35`) — the **marketplace listing manifest**, consumed by `/plugin marketplace add <owner>/<repo>`. Fields: `name`, `id`, `owner.name`, `metadata.description`/`metadata.version` (a *third* description, marketplace-browsing copy), and `plugins[]` — an array of plugin entries, each with its own `name`, `source` (`"./"` = same repo), `description` (a *fourth* variant), `version`, `author`, `keywords`, `category`, `strict`. One marketplace.json can list multiple plugins; here it lists one.
  - Net effect: this repo carries **four independently-maintained copies of "what this skill does"** (skill.json, plugin.json, marketplace.json, SKILL.md frontmatter) that were visibly out of sync at the time of reading — e.g. marketplace.json says "96 palettes"/"13 stack guidelines" while SKILL.md says "161 color palettes"/"10 stacks" (`marketplace.json:8`, `.claude/skills/ui-ux-pro-max/SKILL.md:2`). This is a maintenance smell, not a pattern to copy.
- `.claude/skills/ui-ux-pro-max/SKILL.md` frontmatter (`SKILL.md:1-3`) — only two keys present: `name`, `description`. No `argument-hint`, `license`, or `metadata` on the flagship skill. Other skills bundled in the *same repo* (`.claude/skills/banner-design/SKILL.md:1-6`, `.claude/skills/design/SKILL.md:1-6`, etc. — apparently a different, unrelated "claudekit" (`ckm:`-namespaced) skill set that got vendored alongside) *do* use `argument-hint`, `license: MIT`, and `metadata: {author, version}`. So the fuller frontmatter schema exists and is legal, it's just unused on the main skill.
- The `description` field is the activation mechanism, confirmed by Anthropic's own docs (see §2): it's injected into the system prompt for every installed skill at all times, and Claude matches the current task against it to decide whether to load the rest of SKILL.md. Upstream's description (`SKILL.md:2`, 1000+ characters) is a deliberately keyword-dense wall — "Actions: plan, build, create, design, implement, review, fix, improve, optimize, enhance, refactor, and check UI/UX code. Projects: website, landing page, dashboard..." — optimized for recall against many possible phrasings, not for human readability.
- `.github/workflows/` has **no build/release pipeline**. `claude.yml` is the `@claude` mention-bot (`claude-code-action`) for answering PR/issue comments; `python-package-conda.yml` runs `flake8` + `pytest` on push. `claude-code-review.yml` (not inspected in detail, same family) is an automated PR reviewer. There is no workflow that runs `npm publish` or pushes marketplace updates — those are evidently manual (`README.md:265-294` documents `npm install -g uipro-cli` as a manual step, and `CLAUDE.md:91-98` documents a manual branch→PR→merge git workflow).
- **The `src/` vs `.claude/skills/` vs `cli/assets/` triplication is only partially real** (`CLAUDE.md:30-58, 62-86`):
  - `src/ui-ux-pro-max/` is the **single source of truth** — canonical `data/*.csv`, `scripts/*.py`, `templates/`.
  - `.claude/skills/ui-ux-pro-max/data` and `.../scripts` are **not copies** — they are symlinks to `../../../src/ui-ux-pro-max/data` and `.../scripts` (confirmed: reading these "files" returns the literal relative-path string, because this checkout has git symlinks materialized as plain text files, i.e. Windows checked them out without `core.symlinks=true` / Developer Mode). `.factory/skills/` and `.shared/` are described as symlinks the same way. **On a Windows machine without symlink support enabled, this repo's own skill is broken as checked out** — `data` and `scripts` are unreadable text stubs, not directories. This is a direct, load-bearing warning for our own repo design if we ever rely on symlinks for a Windows audience.
  - `cli/assets/` is a **genuine, intentionally-duplicated copy**, kept in sync by a manual `cp -r` step documented in `CLAUDE.md:78-83`, run "before publishing." It exists because the npm-published `uipro-cli` package needs the data/scripts/templates bundled *inside its own npm tarball* — an npm package can't symlink out to a sibling GitHub repo path at install time on an end user's machine. So: symlinks solve the "same repo, multiple logical locations" problem; the CLI copy solves the "ship inside an independently-distributed npm package" problem. Two different problems, two different solutions.
  - `src/ui-ux-pro-max/data/_sync_all.py` (`_sync_all.py:1-9`) is **not part of the triplication sync** at all — its docstring says it's a one-off maintenance script to keep `colors.csv` and `ui-reasoning.csv` row-aligned with `products.csv` after edits (renumbering, add/remove rows to match). It is a data-consistency tool the authors ran by hand during CSV edits, unrelated to the CLI publish step.
  - Bottom line for our design: **three copies exist because two different distribution channels (a git-based plugin/marketplace and an npm-published CLI) each need their own materialized copy, and a same-repo skill folder is kept in sync via symlink rather than by generating content.** If we don't need an npm CLI, we don't need this pattern at all.
- Templates (`src/ui-ux-pro-max/templates/base/skill-content.md`, 357 lines; `quick-reference.md`, 296 lines; `templates/platforms/*.json`, 19 files) are the CLI's code-generation layer: `uipro init --ai <platform>` reads a platform JSON (e.g. `templates/platforms/claude.json:1-21` — has its own `frontmatter.description`, a **fifth** description variant, plus `sections.quickReference: true`) and stitches `skill-content.md` + conditionally `quick-reference.md` into a platform-specific `SKILL.md`. Per `CLAUDE.md:74-75`, `quick-reference.md` is explicitly "Claude only" — it adds the CLI-command cheat-sheet section that assumes bash/Python execution, which is why it's gated per-platform rather than universal.

### 1.2 Runtime constraints in the Claude app (verified against Anthropic's current official docs, fetched live 2026-09-07)
Sources: [Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview), [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [Skills overview (claude.com)](https://claude.com/docs/skills/overview), [Creating custom Skills (support)](https://support.claude.com/en/articles/12512198-creating-custom-skills).

- **Scripts do execute in the claude.ai app — confidence: High.** Custom Skills in claude.ai require "code execution enabled" (Pro/Max/Team/Enterprise plans) and run "in a code execution environment where Claude has filesystem access, bash commands, and code execution capabilities." Claude reads SKILL.md via bash, and when instructions reference a script, "Claude runs them through bash and receives only the output" — the script's own code never enters context. So a 48KB `design_system.py`-style script is exactly the intended use case, *provided the user's account has code execution turned on*. Network access inside that container is **not guaranteed**: official text is "Depending on user/admin settings, Skills may have full, partial, or no network access" — package installs from PyPI/npm and GitHub pulls are described as *possible* but conditional on that network setting, not a given. Design implication: any script we ship must have a working degraded path if network is off, and must not assume any package beyond Python's standard library unless we tell the user to expect a `pip install` step to succeed.
- **Loading model — confidence: High.** It is confirmed three-tier progressive disclosure, not always-in-context:
  1. Level 1 (always loaded, ~100 tokens/skill): only `name` + `description` from frontmatter, for every installed skill, all the time.
  2. Level 2 (loaded only when the task matches the description): the SKILL.md body. Anthropic's own budget guidance: **keep the body under 500 lines**; one part of their docs also frames it as "under 5k tokens." Upstream's 45KB / 658-line SKILL.md (`ui-ux-pro-max/SKILL.md`) is roughly 30% over that guidance in line count and likely well over the token guidance — it is not "wrong" (nothing enforces the limit) but it is explicitly the anti-pattern the best-practices doc warns against, and their own `templates/base/skill-content.md` + `quick-reference.md` split shows they're aware the router file is large.
  3. Level 3 (loaded only on demand): bundled files. Scripts run via bash with only stdout entering context; markdown reference files are read (and cost tokens) only if Claude actually opens them; "no practical limit on bundled content" because unopened files cost zero tokens. This is why upstream can ship 161-row CSVs without context penalty — as long as the script (not the model) does the CSV parsing and only prints the relevant rows back.
- **Can bundled reference files/CSVs be read at runtime — confidence: High, yes**, either by Claude reading them directly as text (cost = tokens for what's read) or by a script parsing them and returning a filtered result (near-zero cost). Both patterns are explicitly documented and both appear in upstream's own design (`search.py` does BM25 search over the CSVs so the model never has to read all 161 rows itself).
- **Frontmatter validation constraints — confidence: High, directly quoted from platform docs, but conflicts with one secondary source (flag below):**
  - `name`: max 64 chars, lowercase letters/digits/hyphens only, no XML tags, cannot contain the literal words "anthropic" or "claude". **This means upstream's own bundled skills using `ckm:banner-design`-style names with a colon (`.claude/skills/banner-design/SKILL.md:1`) would not validate as a claude.ai-uploaded custom Skill under the documented rule** — colon is not in the allowed character set. This may be tolerated inside a Claude Code plugin (namespacing convention) even though the general Agent Skills spec forbids it for direct upload; we could not fully reconcile this and flag it as an open question.
  - `description`: platform docs say max 1,024 characters, non-empty, no XML tags. **Conflict:** a Claude support-article summary we fetched separately states the claude.ai upload UI enforces "Maximum 200 characters" for description — this may be a stricter UI-level cap specific to the manual-zip-upload flow in Settings, distinct from the general spec limit. We did not find a single source reconciling both numbers. **Confidence: Medium** on the 1,024 figure being the universal ceiling; **Low** on whether claude.ai's upload form silently truncates or rejects past 200. Upstream's own description is already ~1,050 characters (`SKILL.md:2`), i.e. it may already exceed whichever limit actually governs claude.ai upload — this is worth a real test (see §5).

### 1.3 Open-source distribution — the install path for a non-technical user
- Upstream's README (`README.md:254-299`) documents **exactly two install paths, and neither one targets claude.ai**: (a) `/plugin marketplace add nextlevelbuilder/ui-ux-pro-max-skill` + `/plugin install ui-ux-pro-max@ui-ux-pro-max-skill` — a **Claude Code slash command**, not usable in the consumer chat app; (b) `npm install -g uipro-cli` + `uipro init --ai claude` — a **Node CLI** that writes files into a local project folder, again a Claude-Code-shaped (or other coding-agent-shaped) workflow assuming a terminal and a project directory. There is no documented "how a claude.ai user installs this" path in their own README at all.
- Confirmed from Anthropic's docs (§1.2 sources): the actual claude.ai install path is **Customize → Skills → Add**, uploading a **ZIP file** whose root is the skill folder itself (not nested one level deeper), containing `SKILL.md` (lowercase per the support article vs. `SKILL.md` uppercase per platform docs — another minor inconsistency across Anthropic's own surfaces) plus any scripts/resources. This is a **manual, per-user, per-account action** — confirmed explicitly: "Custom Skills are individual to each user. They are not shared organization-wide and cannot be centrally managed by admins," and "Skills uploaded to claude.ai must be separately uploaded to the API" (no cross-surface sync). There is no claude.ai equivalent of a git-based marketplace `/plugin marketplace add` flow.

## 2. Transferable
- **The description-as-router pattern.** Regardless of surface, writing one dense, keyword-rich, third-person `description` field that names both *what* the skill does and *when* to invoke it is the single highest-leverage lever for reliable activation, and it costs ~100 tokens forever once installed. We should adopt this directly — our description needs to name concrete triggers ("PowerPoint deck," "CV," "brochure," "looks like AI slop," "report layout") the same way upstream enumerates UI element names.
- **Progressive disclosure via a thin router SKILL.md + separate reference files**, one level deep (SKILL.md → `reference/X.md`, never `reference/X.md → Y.md`). Upstream's own best-practice violation (658-line monolith) is the counter-example to avoid, not to copy; the *pattern* (router file + `references/`) that Anthropic's own docs prescribe, and that upstream half-executes via `templates/base/skill-content.md` + `quick-reference.md`, is what we should copy.
- **A generate-then-inherit script pattern is compatible with claude.ai**, confirmed by §1.2: a Python script that reads a small set of inputs (e.g. brand colors, doc type) and deterministically emits a design-token file the rest of the skill then reads is exactly the sanctioned "Level 3, executed via bash, output-only" use case. This directly supports the brief's most-valued mechanism (brand-identity generator → inherited by downstream documents) — no redesign needed to make that idea "work" technically, only to build the content.
- **One canonical source directory, no CLI-driven triplication**, unless we actually ship an npm-published installer (see Gaps). If our only distribution targets are (a) a manual claude.ai ZIP upload and (b) an open-source repo a technical user can `git clone`/copy from, we need **at most one skill folder**, not three. Upstream's triplication is a symptom of supporting 18 platforms via one CLI; we are explicitly not doing that (brief: claude.ai primary, ChatGPT secondary/out of scope for packaging).
- **MIT LICENSE + copyright header at repo root** (`LICENSE:1-22`) is the correct, minimal attribution mechanic if we ever verbatim-copy any upstream text/data: keep their notice attached to the copied artifact, or better, don't copy verbatim at all and independently author our own CSVs/prompts (the brief already leans this way).

## 3. Breaks
- **The entire CLI/npm/`uipro init --ai <platform>` distribution model does not transfer.** It assumes a terminal, a project directory, and an agent that reads local project files (Claude Code, Cursor, etc.). claude.ai has no filesystem for a CLI to write into and no slash-command plugin installer — a non-technical user can't run `npm install -g` anything. This is the single biggest structural mismatch between upstream's design and our target surface.
- **`/plugin marketplace add` / marketplace.json discovery does not transfer.** claude.ai's custom-skill upload has no marketplace/listing concept at all today — it's a private, per-account ZIP upload via Settings. `.claude-plugin/marketplace.json`'s entire reason to exist (multi-plugin listing, `strict` flag, `category`) is Claude-Code-specific.
- **Symlinked skill folders (`.claude/skills/.../data` → `../../../src/...`) do not transfer to a ZIP upload.** A ZIP is a flat archive; whatever we put in it must be real files, not symlinks, and — per the Windows evidence in §1.1 — we should not rely on symlinks even in our *authoring* repo if a Windows contributor might ever zip it up directly, since git-on-Windows can silently materialize symlinks as broken text stubs.
- **The bash-driven `python3 skills/.../search.py ...` invocation pattern is surface-conditional, not universal.** It works in claude.ai *only if the user's account has code execution enabled* (Pro/Max/Team/Enterprise — not free tier) *and* only if we don't assume network-dependent pip installs will succeed, since network access is admin/user-configurable and not guaranteed. Upstream's SKILL.md (`SKILL.md:312-325`) even instructs Claude to check for and `brew install`/`apt install` Python if missing — that entire branch is nonsensical inside a claude.ai sandboxed container (no brew/apt, no persistent machine to "install for next time") and should not be copied; it's a Claude-Code-on-a-real-machine assumption leaking into the skill text.
- **The 45KB/658-line single-file SKILL.md does not transfer cleanly** — it works today because nothing *hard-blocks* over-500-line files, but it directly contradicts Anthropic's stated token-budget guidance for optimal performance, and paying that cost on every single activation (Level 2 loads the whole body, not just the relevant section) is a real, ongoing tax we should not inherit.
- **Four-copies-of-the-description drift** (skill.json vs plugin.json vs marketplace.json vs SKILL.md, §1.1) is a bug pattern (observed already out of sync on this checkout), not a transferable practice.

## 4. Gaps
- **No claude.ai-native "install" affordance exists to design around** beyond the manual ZIP-upload UI — there is nothing for us to build that makes this easier for a non-technical user *within* claude.ai itself; our only lever is making the ZIP-prep step (folder → ZIP, correct root) as close to zero-effort as possible (e.g., ship a pre-zipped release artifact in GitHub Releases so the user downloads one file and uploads it, rather than making them clone a repo and zip it themselves).
- **No verified answer on whether claude.ai's upload form enforces the 1,024-char or 200-char description limit** — this gates how dense we can make our activation description; needs a direct test before we finalize copy (see §5).
- **No verified list of pre-installed Python packages in the claude.ai code-execution container** (the API's code-execution tool documents its own package list, but claude.ai's consumer-facing container is not confirmed to be the identical environment). If we want a script to use e.g. `python-pptx` or `python-docx` to emit real Office files, we don't yet know whether that import will simply work, require a user-triggered `pip install` (possible per docs, but conditional on network), or fail outright. This is the load-bearing unknown for the brief's open question about real .docx/.pptx vs. HTML/PDF output — it belongs here and in §5, not assumed either way.
- **No build/release pipeline is needed nor should be copied** — upstream doesn't actually have CI/CD for its releases either (only lint/test CI); if we want reproducible ZIP releases we'd have to build that ourselves (e.g., a simple GitHub Action that zips the skill folder into a Release asset on tag push) — upstream gives us nothing to crib here since they don't do it.
- **No README/onboarding copy exists yet for "how do I put this in claude.ai"** — a good README for this project needs, at minimum: (1) a one-paragraph "what this does," (2) a direct download link to a pre-built `<skill-name>.zip` Release asset, (3) exact steps "Settings → Customize → Skills → Add → select the zip," (4) the code-execution-enabled prerequisite and which plans have it, (5) MIT license + short "built by studying UI/UX Pro Max's architecture (MIT, Next Level Builder), no upstream code or data reused" attribution note. None of this exists yet; upstream's README is structurally the wrong shape to imitate since it's CLI/platform-matrix-first.

## 5. Open questions
- **Does claude.ai's Skills upload UI cap `description` at 200 characters or 1,024?** Settle by: uploading a test skill ZIP with a description of, say, 600 characters and observing whether the UI truncates, warns, or rejects it. (Requires a Pro/Max/Team account with code execution enabled — the user has this via their existing UI/UX Pro Max usage.)
- **What Python (or Node) packages are actually importable, out of the box, inside a claude.ai custom-skill's code-execution container** — specifically `python-pptx`, `python-docx`, `reportlab`/`weasyprint` (for PDF), and whether a `pip install <pkg>` inside a script actually succeeds given the account's current network-access setting. Settle by: shipping a minimal test skill with a script that does `import pptx; print(pptx.__version__)` (and repeat for the others) and running it live in claude.ai.
- **Does the colon-namespaced skill name convention (`ckm:banner-design`) actually work anywhere**, given the documented `name` charset (lowercase/digits/hyphens only) appears to forbid it? Settle by: checking whether that convention is a Claude Code-only plugin-namespacing display convention (i.e., the colon is stripped/interpreted specially by the plugin loader and never reaches the raw `name` field validator) vs. a claude.ai upload rejection. Would need either Anthropic's plugin-loader source or a direct upload attempt.
- **Real .docx/.pptx output vs. HTML/PDF terminus (the brief's central open fork)** cannot be resolved by this packaging research alone — it hinges entirely on the container-package-availability question above. If `python-pptx`/`python-docx` are confirmed available and reliable, real Office files become viable and arguably strictly better than HTML for a "hand this to a non-technical person" product; if not, HTML→PDF (matching upstream's own terminus) is the safe fallback. Flagging this back to whoever owns output-format decisions rather than assuming.
- **Whether claude.ai enforces the ZIP "root is the skill folder, not a subfolder" rule strictly (reject vs. silently misread)** was stated by a support article we fetched via a summarizing tool rather than read verbatim in full; worth a direct look at the source support article ourselves if precise failure-mode behavior matters for authoring a foolproof "how to zip this" instruction in our README.

## Short: ChatGPT parity (secondary, per brief)
No primary-source verification was done here (out of scope per brief; general-knowledge-level only, **confidence: Low-Medium**, treat as directional):
- Nearest equivalents are **Custom GPTs** (system prompt + uploaded knowledge files + optional Actions/API calls; retrieval over knowledge files is reported as inconsistent, not full-context) and **Projects** (project-level instructions + files loaded more fully into context, closer in spirit to a "skill" but without progressive disclosure or bundled executable scripts as a first-class concept).
- What degrades: no equivalent progressive-disclosure/bundled-script architecture — a GPT's "knowledge" files are retrieved, not filesystem-navigated, so a large reference CSV can't be selectively grep'd by the model the way a Claude Skill script can; any script-driven generation step (our brand-identity generator) would need to be re-expressed as a GPT Action calling out to an externally-hosted service, or dropped in favor of ChatGPT's native Code Interpreter/data-analysis mode, which does support real code execution and file generation but is not "installable" as a shareable package the way a Skill or Custom GPT is.
- Recommendation (directional, not decided here): treat ChatGPT as "re-author the instructions as a Custom GPT system prompt + knowledge files" rather than "port the skill package" — there is no packaging format to carry over.
